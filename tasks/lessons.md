### 2026-04-08: KEV pipeline silently broke for 13 days
- **What went wrong:** `fetch-vulnerabilities.yml` pushed `pending_review.json` to PR branches, but the AppSec CVE Reviewer trigger reads from main. PRs were never auto-merged, so pending CVEs accumulated on branches for 13 days without being published. Homepage showed "Updated Mar 26 · Checked Apr 8".
- **What's correct:** Fetch workflow now pushes `pending_review.json` directly to main. No intermediate PR branches — the trigger IS the reviewer, so human-review PRs were redundant.
- **Prevention rule:** Added `check_kev_pipeline_health()` to `audit_pages.py` — flags P1 action item if `lastUpdated` falls >7 days behind `lastChecked` in `kev-data.json`. Also: when designing automated pipelines, verify that every step can actually read the output of the previous step (same branch, same file location).

### 2026-06-21: One generator crash blacked out the blog for ~2 weeks
- **What went wrong:** `generate_threat_roundup.py` used `float(v.get('cvss', 0))`. A newly-added KEV entry stored `cvss: null` (key present, value None), so `.get` returned None and `float(None)` raised TypeError. `publish-blog.yml` ran its 10 generators sequentially with no error tolerance, so that one crash aborted the whole job before `publish_editorial.py` — no weekly roundup AND no AI-security roundups published from June 9 to June 21. Every other workflow stayed green, so the only signal was a weekly failure email that was easy to miss.
- **What's correct:** Use `float(v.get('cvss') or 0)` (the idiom already in `fetch_kev.py` and `generate_cve_social.py`). `dict.get(k, default)` only defaults on a MISSING key, never on a present-but-null value. Structurally, each generator in `publish-blog.yml` now runs `continue-on-error: true` with a step `id`, and a final `if: always()` gate publishes what succeeded, then fails the job red and names each crashed step.
- **Prevention rule:** (1) Never trust `dict.get(key, default)` to guard against null — only against missing. For nullable values use `(v.get(key) or default)` or an explicit None check. (2) In any multi-step automation where steps are independent, isolate failures (`continue-on-error` + an aggregation gate) so one crash can't take down the rest, and make the failure loud (red job + named culprit), not silent. Regression test: `tests/test_generate_threat_roundup.py`.

### 2026-09-05: Cloudflare's security scanner flagged the site's own working DNS as a vulnerability

**What went wrong:** Cloudflare Security Insights flagged 4 "Dangling A Record" findings (Moderate severity) as vulnerable to subdomain takeover. The 4 IPs were GitHub Pages' own official, currently-active shared IPs (`185.199.108-111.153`) — the site's actual, correct hosting configuration, still serving 200 OK. The scanner's heuristic (other unrelated hostnames also resolve to the same IP) can't distinguish "shared hosting IP legitimately serving your content" from "an abandoned resource someone else could claim," because GitHub Pages (like Netlify, Vercel, Fastly) is multi-tenant by design. Following the scanner's literal "remove this record" recommendation would have taken the live site offline.

**What's correct:** Verified against a full BIND zone export before touching anything — confirmed the flagged IPs matched GitHub's documented custom-domain setup exactly, plus a live 200 response and a real `www` CNAME to `robertflores17.github.io`. Left the records alone. Separately, used the same zone export to find genuinely dead DNS (7 SendGrid records with zero references anywhere in this repo's git history) — a real, safe cleanup, distinguished from the false positive precisely by tracing actual code usage instead of trusting the scanner's verdict either way.

**Prevention rule:** Same standing rule as this file's Bug Bounty Verification Rules, generalized: an automated security scanner's finding is a lead, not a verdict — verify against the actual live configuration (and, for "is this dead code" style findings, the full git history, not just current HEAD) before acting on its recommendation, especially before any change that touches live DNS, and doubly so for the record's own recommended fix if that fix is destructive.

### 2026-06-21: GitHub Actions `set -e` aborted a gate step using `[[ ]] && ...`
- **What went wrong:** The new "Fail if any generator crashed" gate used `check() { [[ "$2" == "failure" ]] && failed="$failed $1"; }`. GitHub Actions runs `run:` blocks with `bash -e`. When an outcome was NOT "failure", the `[[ ]]` returned non-zero, so the function returned non-zero, and `set -e` aborted the step — turning the job red even when every generator and the push succeeded (false alarm on every clean run).
- **What's correct:** Use an explicit `if`: `check() { if [[ "$2" == "failure" ]]; then failed="$failed $1"; fi; }`. An `if` whose condition is false returns 0, so the function is `set -e`-safe.
- **Prevention rule:** Under `set -e` (the Actions default), never end a function or step with a bare `[[ cond ]] && cmd` — it returns the test's exit status, non-zero when the test is false. Use an explicit `if`, or append `|| true`. Always exercise a new workflow step once via `workflow_dispatch` before trusting it — self-QA caught this within minutes.

### 2026-09-17: `generate_guides.py` silently regresses 11 live pages
- **What went wrong:** Planned to regenerate `owasp-llm-top10.html` for the 2026 OWASP refresh by editing `scripts/generate_guides.py` and running it. The run rewrote all 11 pages in `PAGE_CONFIGS` (it has no filter argument) and produced a net **-634 lines**: the live pages had been post-processed since generation by `inject_navbar_rss.py`, `inject_blog_links.py`, `inject_store_ctas.py`, `inject_error_reporter.py` plus hand edits, and the generator knows about none of it. `ai-security-careers.html` alone lost 450 lines. Separately, the generator's `content_html` for the hub still held the pre-migration version (10 inline risk sections, no `AI-VULN-GRID` markers), so the run also deleted the marker block that `generate_ai_vuln_pages.py` requires and would have broken the next pipeline run.
- **Why it was not caught earlier:** `generate_guides.py` is referenced by no workflow and no other script, and it has been crash-on-import broken since 2026-03-06 (`_esc` undefined, never imported). Nobody had run it in six months, so the drift accumulated invisibly.
- **What's correct:** Treat a generator as authoritative only if something actually runs it. For a page the injectors own, edit the live HTML surgically and keep the diff to the lines that changed. Fixed the `_esc` crash and updated the hub's config so a future run is at least correct, but did not use it to produce the page.
- **Prevention rule:** Before running ANY site generator, run it and immediately `git diff --stat` before staging anything. If files you did not intend to change are in the diff, `git checkout --` them and edit surgically instead. A generator that touches more files than your task does is a regression, not a convenience. Corollary: when a one-time migration moves content out of a generator (like `migrate_owasp_llm_content.py` did), update the generator in the same commit or it becomes a landmine.

### 2026-09-17: Published an OWASP framework wrong by trusting secondary sources over the project's own repo
- **What went wrong:** Built 10 pages for the OWASP Agentic Skills Top 10 from a LinkedIn announcement, a personal GitHub fork (`kenhuangus/agentic-skills-top-10`), and a third-party blog. Content Editor blocked the push with 5 P0s. The worst: **AST05 is "Untrusted External Instructions", not "Unsafe Deserialization"** — a whole page describing the wrong risk, duplicating AST04's content, while the real AST05 was absent from the site. Also claimed AST10 was "a security standard published August 17, 2026" when `OWASP/www-project-agentic-skills-top-10/index.md` says "New Project Proposal — active development", Incubator badge, v1.0 targeted Q4 2026. And asserted "AST10 does not assign severity labels" when every `ast0N.md` carries an explicit `**Severity**:` line (two of my ratings contradicted the official ones).
- **The tell I ignored:** my first source (the LinkedIn article, written by the project lead) said "Untrusted External Instructions". A later fetch of a *personal fork* said "Unsafe Deserialization". I picked the fork over the announcement and wrote "two detailed sources agree" in my own summary, when the two sources were the fork and a blog that had copied it. I never fetched the OWASP org repo, which is free, public, and definitive.
- **Prevention rule:** For ANY OWASP/NIST/CIS/MITRE framework, fetch the standards body's own repo or site FIRST and treat it as the only authority for names, numbering, severities, and status. `raw.githubusercontent.com/OWASP/<project>/main/*.md` is one request. Secondary sources are for narrative colour, never for taxonomy. When two sources conflict on a name, that is a hard stop for direct verification, not a vote to resolve by count. And check project *status* before calling anything "published" or "a standard" — Incubator is not released.
- **Second-order rule:** verify every CVE ID and CVSS score against the NVD API even when an upstream standard supplies it. Two errors here were inherited from OWASP's own markdown: it maps ClawJacked to CVE-2026-28363 (NVD says that ID is a `sort` allowlist bypass) and garbles Snyk's 13.4% figure (share of scanned skills with critical issues, not an escape rate). The project's existing KEV rule already says this; it applies to standards prose too. All three CVSS scores I published were CNA secondary scores, not NVD primary: 8.7 vs 8.8, 5.3 vs **7.5** (Medium vs High), 9.9 vs 8.8.

### 2026-09-19: Wrote a vendor import file and dashboard steps from memory instead of the format reference
- **What went wrong:** Prepared Cloudflare Bulk Redirects for the 8 renumbered OWASP LLM URLs and got it wrong three times in a row, each caught by Robert rather than by me. (1) Sent him to **Manage Account → Configurations → Lists**, which only creates **IP** lists — so the list came out as the wrong type, consumed the account's single list slot, and produced a "you have reached your custom list limit" banner that looked like a plan problem but was my bad instruction. Bulk Redirect Lists are created from the separate **Bulk Redirects** page. (2) The CSV carried a **header row**; Cloudflare's format has none, so the header would have imported as a 9th bogus redirect. (3) The CSV prefixed the **source** URL with `https://`; source takes host + path only, and only the target is a full URL.
- **Why it happened:** I generated the file and wrote the click-path from prior familiarity, then read `developers.cloudflare.com/.../csv-file-format/` only after he hit the error. Every one of the three mistakes was answered verbatim on a doc page I had not opened. I also verified the wrong things thoroughly — I curled all 16 URLs to prove the redirect targets were live, which was real work that could not catch a format error.
- **Prevention rule:** Before writing ANY file another system will import (CSV, YAML, manifest, upload template) or giving a click-path through someone else's dashboard UI, open that vendor's current format/UI reference first and cite it. Treat "I know this format" exactly like "I know this figure" — the existing rule that bans round-number guesses in copy applies to file formats and navigation paths too. A generated import file is not verified by checking that its *contents* are semantically right; it is verified against the consuming system's schema.
- **Also:** when a vendor UI shows a limit or entitlement error right after following my instructions, suspect my instruction before the user's plan. Here the `1/1` list limit was real but irrelevant — the actual fault was creating the wrong list type on the wrong page.
